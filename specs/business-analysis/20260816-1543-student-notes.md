## Background / Context

The Student Notepad (ශිෂ්ය සටහන් පොත) is described in `docs/student-notes.md` as **"the most important implementation of this project"** — the workspace where a student makes the observations that lead to a prediction. Today the platform computes and displays horoscope data (charts, warga kendara, shad bala, bhava suchika, dashas), but it offers no per-horoscope study workspace. This feature adds one:

- A **notepad popup** on the horoscope detail page that the student can **move and resize**, with tags for each **house purpose** (12 houses + "Other").
- **Only one parent tag is selectable at a time**; selecting a parent reveals its **sub-tags** (the house significations, e.g. parent "1 — The person" → Self, Body, Personality, Identity, Vitality, Appearance, …).
- Selecting a sub-tag makes the system show **observations of the horoscope** derived from the existing `CalculatedDetails` data:
  - The **planets and details** of each planet in the house
  - **House load, house load position, Nakshatra load of the house load, position of the Nakshatra load**
  - The **planet(s) and details relevant to the sub-tag** (planet significations)
  - **Chandra Lagna's** related house + house load + position + details (e.g. for Marriage check the 7th house of the Chandra chart)
  - **Surya Lagna's** related house + house load + position + details
  - The **related Warga Kendara** and its data: warga Lagna + load + position; the related house of the warga chart + load + position; the **D1 load** in the warga chart + position + details
- Observations render as **tags with colors** — green when the strength is good, red when bad, white otherwise — and **each sub-section shows its ratio** as `(green tags count/all tags count)` e.g. `(3/6)` (no division performed).
- The student can additionally add **their own observation tags** (with a selectable color) and, based on all observations, add **result notes**.

**Design posture (mirroring the Warga Kendara and Shad Bala precedents):**

- The **house-purpose catalog** and the **planet-signification catalog** are static, system-wide reference data resolved via i18n (like the Varga Chart Catalog) — never stored per horoscope, never user-editable. English/Sanskrit is authoritative from the feature doc; Sinhala strings are pending domain confirmation.
- The **system-generated observations are derived, not persisted**: pure render-time functions over the already-shipped `CalculatedDetails` payload (including `wargaKendara`) — the `currentPlanets`/`wargaKendara`-fallback precedent. Color classification and `(n/m)` ratios are also render-time. *Caveat:* the "house load" / "Nakshatra load" concepts are not defined anywhere in the repository — the derivation depends on a domain definition (Open Questions 1–2). If the load values cannot be derived from existing stored fields, they would become new derived fields on `CalculatedDetails` recomputed by the AstrologySettings recalculation job.
- **Student-entered data lives on a new `HoroscopeNote` document** — one per (student, horoscope), private to the student (SearchBookmark precedent), never touched by the recalculation job (Shad Bala `overridden` precedent).

## Student Notepad Actors

### Student

- **Description**: An astrology student who studies horoscopes and records observations to form predictions.
- **Notepad-Specific Goals**: Open a movable/resizable notepad on any horoscope they can view, drill into a house topic (parent tag → sub-tag), read the system's derived observations for that topic, add their own colored observation tags, and write result notes.
- **Notepad-Specific Permissions**:
    - Open the Student Notepad popup on any viewable horoscope (own, public, share-linked) and move/resize it; geometry persists per horoscope
    - Select a single parent tag (12 house purposes + "Other") and drill into its sub-tags
    - View system-generated observations for the selected sub-tag as color-coded tags (green = good / red = bad / white = neutral) with per-section `(n/m)` ratios
    - Add own observation tags with a selectable color; edit/delete own observation tags
    - Add/edit/delete result notes based on all observations
    - Persist the notepad per horoscope (geometry, observation tags, result notes) — private, never visible to other viewers

### System (Calculation Engine)

- **Description**: Automated services that supply derived observation data and static catalogs.
- **Notepad-Specific Responsibilities**:
    - Maintain the static house-purpose catalog (13 parent tags: 12 houses with Sanskrit name + main purpose/significations → sub-tags, plus "Other") — bilingual display data via i18n, never stored per horoscope
    - Maintain the static planet-signification catalog (Sun → self/soul/father…, Moon → mind/mother…, etc.) and the reverse sub-tag → relevant planet(s) mapping
    - Derive the system observation payload for a selected parent/sub-tag from `CalculatedDetails` (both `source: "auto"` and `source: "manual"`, legacy fallback): planets in the house; house load + position; Nakshatra load + position; sub-tag planet significations; Chandra/Surya Lagna related house + load + position; related Warga Kendara (warga lagna, related house, D1 load in the warga chart) + loads + positions + details — on-the-fly pure functions, never stored on the note document
    - Classify each derived observation as good (green) / bad (red) / neutral (white) and compute each section's `(green/all)` ratio at render time

### US-SN-001: Notepad popup — open, move, resize

- **Title**: The Student Notepad opens as a movable, resizable popup on the horoscope detail page
- **Story**: As a student, I want a notepad popup on the horoscope detail page that I can move and resize, so that I can take observations while keeping the chart data visible.
- **Priority**: High
- **Actor**: Student
- **Dependencies**: Notepad entry point on the horoscope detail page; `HoroscopeNote.notepadState` persistence (US-SN-013)

#### Acceptance Criteria

1. **Open/close**:
    - Given a horoscope detail page, When the student clicks the notepad button, Then a notepad popup opens above the page content; clicking the button again (or a close control) closes it
    - Given the popup is closed, When the student reopens it on the same horoscope, Then it restores the last saved position, size and open content

2. **Move**:
    - Given the popup is open, When the student drags it by its header, Then it follows the pointer and stays within the viewport bounds (clamped — never fully off-screen)

3. **Resize**:
    - Given the popup is open, When the student drags the resize handle, Then the width/height change within the configured minimum and maximum bounds

4. **Geometry persistence**:
    - Given the student moved/resized the popup, When the popup is closed and later reopened on the same horoscope, Then position and size restore to the saved values

5. **Content follows the horoscope**:
    - Given the notepad is open on horoscope A, When the student navigates to horoscope B, Then the notepad switches to horoscope B's own saved geometry, tags, notes and selection state — and the system observations re-derive from horoscope B's calculated data, never horoscope A's
    - Given two horoscopes are open in different tabs, When the student saves content in one tab, Then it persists only to that horoscope's note document

#### Edge Cases

- **First open**: no saved geometry → the popup opens at a sensible default position/size (centered or docked — UX decision)
- **Small viewport / mobile**: the popup clamps to the viewport; touch-drag and touch-resize behave predictably (UX decision for touch targets)
- **Horoscope switch**: navigating to another horoscope uses that horoscope's own saved geometry (or the default when none exists), its own tags/notes and its own re-derived observations — no cross-horoscope bleed
- **Rapid drag/resize**: pointer events settle on the final geometry without jitter; saving is debounced or on close (implementation choice)

#### Business Rules

- Geometry is stored per (student, horoscope) on `HoroscopeNote.notepadState` — private to the student
- The popup is non-modal over the horoscope detail page (the chart data stays visible behind it)

### US-SN-002: Parent tag strip — single selection and sub-tag drill-down

- **Title**: One parent tag at a time; selecting it reveals its sub-tags
- **Story**: As a student, I want exactly one parent tag selectable at a time — the 12 house purposes plus "Other" — and to see that parent's sub-tags after selecting it, so that I can focus my observation on one house topic at a time.
- **Priority**: High
- **Actor**: Student
- **Dependencies**: US-SN-003 (house-purpose catalog)

#### Acceptance Criteria

1. **Parent tag strip**:
    - Given an open notepad, When the tag strip renders, Then it shows all 13 parent tags — "1 — The person" … "12 — What he/she releases" plus "Other" — labelled from the static house-purpose catalog (bilingual)

2. **Single selection (radio behaviour)**:
    - Given no parent selected, When the student clicks a parent tag, Then it becomes selected and its sub-tags appear
    - Given a parent is selected, When the student clicks a different parent tag, Then the previous selection is deselected and the new parent's sub-tags appear (only one parent selected at any time)
    - Given a parent is selected, When the student clicks the same parent again, Then nothing changes (no-op — it stays selected)

3. **Sub-tag drill-down**:
    - Given parent "1 — The person" is selected, When its sub-tags render, Then they show Self, Body, Personality, Identity, Vitality, Appearance, Overall life direction (the significations of the 1st house from the catalog)
    - Given the "Other" parent is selected, When the sub-tag area renders, Then no house sub-tags appear — the "Other" area shows the student's free-form observation tags (see US-SN-011)

4. **Observation trigger**:
    - Given a sub-tag is selected, When the system observations render, Then they reflect the selected parent house and sub-tag (US-SN-004…US-SN-009)

#### Edge Cases

- **Long labels**: Sinhala parent labels wrap or scroll horizontally without breaking the strip (UX decision)
- **Keyboard navigation**: the strip is keyboard-operable (`aria-pressed` toggle semantics, consistent with the warga tab strip precedent)
- **Parent without sub-tags** ("Other"): selecting it never shows an empty sub-tag row — it shows the Other observations area instead

#### Business Rules

- Parent-tag values are numeric: `0` = "Other", `1`-`12` = house number (no separate enum; the house number is the value)
- Sub-tag labels come from the static catalog (i18n keys), never stored per horoscope and never user-editable
- Selection state is client-side; optional persistence in `notepadState.selectedParentTag`/`selectedSubTag` (UX decision — see Open Questions)

### US-SN-003: Static house-purpose catalog

- **Title**: The 12 house purposes and their significations come from a static bilingual catalog
- **Story**: As a student, I want the parent tags and sub-tags to come from the authoritative house table — house number, Sanskrit name, main purpose/significations — so that the taxonomy matches the feature document exactly.
- **Priority**: High
- **Actor**: System
- **Dependencies**: Static catalog data (see `data-model.md` → House Purpose Catalog)

#### Acceptance Criteria

1. **Catalog-sourced tags**:
    - Parent tags and sub-tags render exactly from the house table in `docs/student-notes.md` — house `1` Tanu/Lagna "The person" → Self, Body, Personality, Identity, Vitality, Appearance, Overall life direction … house `12` Vyaya/Mokṣa "What he/she releases" → Expenditure, Loss, Foreign places, Isolation, Sleep, Spiritual liberation, Letting go; plus "Other" (no house, no sub-tags)

2. **Sanskrit names**:
    - Each parent tag carries its Sanskrit name (Tanu/Lagna, Dhana, Sahaja/Bhrātṛ, Sukha, Putra, Ari/Ṣaṭru, Yuvati/Kalatra, Randhra/Ayu, Dharma/Bhāgya, Karma, Lābha, Vyaya/Mokṣa) resolved via i18n per locale

3. **Bilingual**:
    - Parent labels, sub-tag labels and Sanskrit names render in Sinhala or English per the active locale (existing `useI18n()` re-render behaviour); English is authoritative, Sinhala pending domain confirmation with English fallback (existing convention)

#### Edge Cases

- **Missing translation**: an untranslated catalog entry falls back to English (existing i18n behaviour)
- **Sub-tag lookup**: a sub-tag selected by the student is stored by its catalog key, so a later catalog wording change does not break stored tags

#### Business Rules

- The catalog is static, system-wide reference data — resolved via i18n message keys, never stored per horoscope, never user-editable (Varga Chart Catalog precedent)
- Sub-tag identity is the catalog **key** (stable string), not the localized display text

### US-SN-004: System observations — planets in the house

- **Title**: The planets of the selected house (D1) show as colored tags with their details
- **Story**: As a student, when I select a sub-tag under house N, I want to see the planets placed in house N of the Rāśi (D1) chart with each planet's details, so that I can observe the house's planetary picture at a glance.
- **Priority**: High
- **Actor**: Student, System
- **Dependencies**: US-SN-002; `CalculatedDetails.planets` / `wargaKendara.d1.houses[].planets`; US-SN-010 (colors + ratio)

#### Acceptance Criteria

1. **Section content**:
    - Given a sub-tag under parent house N is selected, When the "planets in the house" section renders, Then it lists every planet placed in house N of the D1 chart (whole-sign placement as stored)
    - Each planet tag shows the planet, its sign, strength, house, Nakshatra (Pada), conjunctions and aspects — numeric enums resolved to bilingual display names

2. **Tag color**:
    - Each planet tag renders green/red/white per the confirmed classification rule (US-SN-010)

3. **Ratio**:
    - The section header shows the ratio `(green count/all count)` for the section, e.g. `(1/2)`

4. **Both chart sources**:
    - The section derives correctly for `source: "auto"` horoscopes and for `source: "manual"` horoscopes (from the entered placements)

#### Edge Cases

- **Empty house**: no planets → a single neutral tag ("no planets in this house") or the section renders empty — UX decision; the ratio shows `(0/0)` or the section is omitted
- **Rahu/Ketu in the house**: nodes appear exactly like other planets (they have no sign lordship, but their placement still shows)

#### Business Rules

- Data source is the stored D1 planets/houses (auto: calculated; manual: `manualHousePlacements` via the existing warga derivation)
- Details shown are the existing per-planet fields — no new calculations in this story

- **Title**: House load, house load position, Nakshatra load of the house load and its position show as colored tags
- **Story**: As a student, I want to see the house load of house N, the house load position, the Nakshatra load of the house load and the position of the Nakshatra load, so that I can judge the house's strength beyond simple planet placement.

### US-SN-006: System observations — sub-tag relevant planet significations

- **Title**: The planet(s) relevant to the selected sub-tag show with their details
- **Story**: As a student, when I select a sub-tag, I want to see the planet(s) whose significations match that sub-tag (e.g. "father" → Sun, "mother" → Moon, "marriage" → Venus) together with their details, so that the observation ties the house topic to its significator planets.
- **Priority**: High
- **Actor**: Student, System
- **Dependencies**: US-SN-002; static planet-signification catalog and reverse sub-tag → planet(s) mapping (US-SN-003 pattern); US-SN-010 (colors + ratio)

#### Acceptance Criteria

1. **Reverse mapping**:
    - Given sub-tag "Self" is selected, When the "relevant planet" section renders, Then it shows Sun (Ravi) — the planet whose significations include "Self" — with its details (sign, strength, house, Nakshatra)
    - Given sub-tag "Marriage" is selected, Then it shows Venus (Shukra) per the planet-signification table

2. **Multiple matches**:
    - Given a sub-tag matches more than one planet (e.g. "wealth" appears in Jupiter's list and as a house signification), When the section renders, Then every matching planet shows as its own tag (all matches, not a curated subset — pending domain confirmation, Open Question 4)

3. **Details and colors**:
    - Each planet tag shows the same detail fields as US-SN-004 and the green/red/white classification
    - The section header shows its `(green/all)` ratio

#### Edge Cases

- **Unmapped sub-tag**: no planet signification matches the sub-tag → a neutral white tag ("no significant planet") rather than an empty section
- **Sub-tag under "Other"**: no planet-signification section renders (the Other parent has no house/sub-tag observations)

#### Business Rules

- The mapping derives from the static planet-signification catalog (reverse lookup on the sub-tag key) — static data, resolved via i18n, never stored per horoscope
- All matching planets render (per the confirmed rule — see Open Questions)

### US-SN-010: Color classification and per-section ratio

- **Title**: Observations render as green/red/white tags with a `(green/all)` ratio per section
- **Story**: As a student, I want every system observation tag colored green when its strength is good, red when bad, and white otherwise, with each sub-section showing its ratio as `(green count/all count)` — e.g. `(3/6)` — so that I can scan the balance of good vs bad indicators.
- **Priority**: High
- **Actor**: System
- **Dependencies**: US-SN-004…US-SN-009 (observation sections); domain confirmation of the classification rule (Open Questions 2–3)

#### Acceptance Criteria

1. **Tag colors**:
    - Given a section renders with observation tags, When each tag's strength is classified, Then a good indicator renders green, a bad indicator renders red, and everything else renders white
    - The classification applies per observation kind (planet strength, house load, Nakshatra load, warga data) per the confirmed domain rule

2. **Ratio display**:
    - Each sub-section header shows the ratio as `(green count/all count)` — e.g. `(3/6)` — counting the section's green tags over its total tags
    - The display is literal `(n/m)` — no division, no percentage

3. **Derived at render time**:
    - Colors and ratios are pure render-time derivations — never stored, never persisted on `HoroscopeNote`

#### Edge Cases

- **All white**: a section with no green and no red tags shows `(0/n)`
- **Empty section**: no tags → the ratio shows `(0/0)` or the section is omitted (UX decision)
- **Classification boundary**: a neutral-strength planet (Sama 0) renders white, not green or red (proposed rule — see Open Questions)

#### Business Rules

- Color is **not** a stored attribute of system observations — it is a render-time classification (contrast with student tags, which store a selectable `TagColor`)
- The classification rule per observation kind must be confirmed by the domain before implementation (Open Questions 2–3)

### US-SN-011: Student's own observation tags with selectable color

- **Title**: The student adds their own observation tags with a selectable color
- **Story**: As a student, based on the system observations, I want to add my own observation tags with a color of my choice, so that I can record my personal findings in the context of the current house topic.
- **Priority**: High
- **Actor**: Student
- **Dependencies**: US-SN-002 (current parent/sub-tag context); US-SN-013 (`HoroscopeNote` persistence)

#### Acceptance Criteria

1. **Add a tag**:
    - Given a parent tag (and optional sub-tag) is selected, When the student enters observation text and picks a color, Then a new observation tag saves into the current parent/sub-tag context with the chosen color
    - Given the "Other" parent is selected, When the student adds a tag, Then it saves with `parentTag = 0` and no sub-tag

2. **Color selection**:
    - When the student opens the color picker, Then the selectable palette (numeric `TagColor` enum) shows; a default color applies when none is chosen (UX decision)

3. **Edit/delete**:
    - Given an existing observation tag, When the student edits or deletes it, Then the change persists (edit keeps the tag's context)

4. **Listing**:
    - Student observation tags list within the notepad, grouped by their parent/sub-tag context so they appear when that context is selected

#### Edge Cases

- **Empty text**: an empty observation tag is rejected (inline validation)
- **Length cap**: text longer than the cap is rejected with a localized message (cap TBD — see Open Questions)
- **Context switch**: a tag added under parent 7 stays under parent 7 — it does not follow the student when they switch parents
- **Concurrent editing**: last-write-wins on the same tag (single-user notepad; no locking)

#### Business Rules

- Student tags are stored on `HoroscopeNote.observationTags` with a numeric `TagColor` enum — never localized text in storage
- Student tags are private to the student (US-SN-014)

### US-SN-012: Result notes

- **Title**: The student writes result notes based on all observations
- **Story**: As a student, after reviewing the system observations and my own tags, I want to add result notes, so that I can record my conclusion/prediction for the horoscope.
- **Priority**: High
- **Actor**: Student
- **Dependencies**: US-SN-011 (observations exist first); US-SN-013 (`HoroscopeNote` persistence)

#### Acceptance Criteria

1. **Add a note**:
    - Given the notepad is open, When the student writes a result note and saves, Then it persists on the notepad and appears in the result-notes list (newest first)

2. **Edit/delete**:
    - Given an existing result note, When the student edits or deletes it, Then the change persists

3. **Notes are distinct from tags**:
    - Result notes render as text entries, visually distinct from the color-coded observation tags

#### Edge Cases

- **Empty note**: an empty result note is rejected (inline validation)
- **Long note**: text wraps; no horizontal scroll (UX decision)
- **No observations yet**: the student can still write a result note (the notes are not gated on observations — pending domain confirmation)

#### Business Rules

- Result notes are stored on `HoroscopeNote.resultNotes` (plain text, notepad-level — per-parent grouping is an Open Question)
- Result notes are private to the student (US-SN-014)

### US-SN-013: HoroscopeNote persistence and lifecycle

- **Title**: The notepad persists per (student, horoscope) and survives recalculations
- **Story**: As a student, I want my notepad — geometry, observation tags and result notes — to persist per horoscope and survive reloads, recalculations and system changes, so that my study progress is never lost.
- **Priority**: High
- **Actor**: System
- **Dependencies**: `HoroscopeNote` entity (see `data-model.md`)

#### Acceptance Criteria

1. **One notepad per (student, horoscope)**:
    - Given a student opens the notepad on a horoscope for the first time, When they save any content or geometry, Then a `HoroscopeNote` document is created for that (user, horoscope) pair
    - A second student opening the notepad on the same horoscope gets their own separate document

2. **Persistence across sessions**:
    - Given saved notepad content and geometry, When the student reloads the page or returns later, Then tags, notes and geometry restore

3. **Cascade delete**:
    - Given a horoscope or user is deleted, When the deletion completes, Then the related `HoroscopeNote` documents are cascade-deleted (SearchBookmark behaviour)

4. **Untouched by recalculation**:
    - Given the AstrologySettings full recalculation job runs, When it processes the horoscope, Then the `HoroscopeNote` document is never written or recomputed (student data, not derived data)

5. **Every student modification is persisted to the database**:
    - Given the student moves/resizes the popup, adds/edits/deletes an observation tag, writes/edits/deletes a result note, or changes the selected parent/sub-tag (when selection persistence is enabled), When the action completes, Then the change is saved to the `HoroscopeNote` document for that (student, horoscope) pair — no modification is ever kept only in memory or the browser session
    - Given the student reloads the page or returns to the horoscope later, When the notepad reopens, Then all previously saved modifications (geometry, selection state, tags, notes) restore from the database

#### Edge Cases

- **Legacy documents**: a horoscope without a `HoroscopeNote` renders an empty notepad (lazy creation on first save)
- **Concurrent saves**: last-write-wins per field group (single-student notepad; no locking)
- **Partial failure**: a failed save leaves the previous state intact (no partial writes)
- **Per-horoscope isolation**: saving on one horoscope never writes to another horoscope's note document (keyed strictly by the (student, horoscope) pair)

#### Business Rules

- `HoroscopeNote` is the only persistent store for notepad student data; system observations are never stored on it (see `data-model.md` → NotepadObservation)
- The document follows the embedded-`{ id: UUID }` reference convention for `user` and `horoscope`

### US-SN-014: Privacy and read-only views

- **Title**: Notepad content is private to the student on every view
- **Story**: As a student, I want my notepad content to be visible only to me — even when the horoscope is public or shared — so that my study notes stay private.
- **Priority**: High
- **Actor**: Student, System
- **Dependencies**: US-SN-013

#### Acceptance Criteria

1. **Private on own horoscopes**:

2. **Private on public horoscopes and share links**:
    - Given a public horoscope or a share link, When a viewer opens the notepad, Then they see their own notepad for that horoscope, never the owner's or any other student's tags/notes

3. **Never in search**:

#### Edge Cases

- **Owner views own public horoscope**: the owner always sees their own notepad (their content, no special casing)
- **Super Admin**: whether Super Admin can read student notepads is an Open Question (default: no — private study notes, mirroring SearchBookmark, unless support requires)

#### Business Rules

- Notepad visibility is scoped to the owning student only; the horoscope's `isPublic`/`displayName`/share-link rules do not extend to notepad content
- No endpoint exposes another student's `HoroscopeNote`

### US-SN-016: System observation derivation from CalculatedDetails

- **Title**: The system derives every observation section from existing calculated data, on both sources, with a legacy fallback
- **Story**: As a student, I want the system observations to derive automatically from the horoscope's calculated data — on auto and manual horoscopes alike, and even for horoscopes stored before the feature existed — so that the notepad always shows the correct picture without manual entry.
- **Priority**: High
- **Actor**: System
- **Dependencies**: US-SN-004…US-SN-009; `CalculatedDetails` (incl. `wargaKendara`); US-SN-010 (classification/ratio)

#### Acceptance Criteria

1. **On-the-fly derivation**:
    - Given a horoscope's `CalculatedDetails` is available on the page, When the student selects a sub-tag, Then every observation section derives via pure functions from that data (planets, houses, nakshatra, `wargaKendara`) — no per-request API call, no loading spinner (data ships with the page render, per the existing detail-page pattern)

2. **Both chart sources**:
    - The derivation works for `source: "auto"` and `source: "manual"` horoscopes; manual horoscopes are limited to what the entered placements support (e.g. no D9 warga section without entered Navamsa data)

3. **Legacy fallback**:
    - Given a horoscope stored before `wargaKendara` existed, When the notepad renders warga-based sections, Then the existing render-time fallback derivation supplies the data — identical UI, no error state

4. **Graceful degradation**:
    - Given a corrupt or partial `CalculatedDetails`, When a section cannot derive, Then it renders a neutral "not available" tag and logs a warning — never a crash

#### Edge Cases

- **Missing calculated details**: the notepad still opens and shows the student's own tags/notes; system sections show the not-available state
- **Domain-pending values**: sections whose derivation depends on the unconfirmed "house load"/"Nakshatra load" definitions render as neutral until the rule is confirmed (Open Questions 1–2)

#### Business Rules

- System observations are pure derived data: computed at render time from stored calculated data, never persisted on `HoroscopeNote`, no user overrides
- If the confirmed load definitions require values not derivable from existing stored fields, those values become new derived fields on `CalculatedDetails` recomputed by the AstrologySettings recalculation job (mirroring `wargaKendara`) — see Open Questions for the Architect

## Clarifying Assumptions

1. **Notepad entry point**: the notepad popup opens from the horoscope **detail page** (the doc says "for each horoscope"; search result cards are out of scope). Each student gets their own notepad per horoscope — the notepad is the student's private study workspace, not horoscope data, so it exists for own, public and share-linked horoscopes alike.
2. **Observations always follow the viewed horoscope**: system observations are derived strictly from the **currently viewed horoscope's** `CalculatedDetails` (incl. `wargaKendara`). Switching horoscopes instantly switches the observations — the notepad never shows another horoscope's data, and the student's saved tags/notes/geometry are keyed to the horoscope they were created on (per-horoscope isolation, US-SN-001 AC5, US-SN-013 AC5).
3. **All student modifications persist to the database per horoscope**: every student change — popup geometry, selection state (when persisted), observation tags, result notes — is written to the `HoroscopeNote` document for that (student, horoscope) pair. Nothing lives only in memory; reopening the notepad on the same horoscope restores everything from the DB (US-SN-013 AC5).
4. **Related house rule**: "Chandra lagna's related house" / "Surya lagna's related house" / "related house of Warga Kendara" = the **same house number as the selected parent tag** in the reference chart (the feature doc's example — "for Marriage need to check 7th house of Chandra chart" — is consistent: Marriage is a 7th-house sub-tag). Pending domain confirmation (Open Question 5).
5. **Sub-tag → planet mapping**: derived by reverse lookup on the static planet-signification catalog — every planet whose signification list contains the sub-tag shows. E.g. "Self" → Sun; "Mother" → Moon; "Marriage" → Venus; "Children" → Jupiter; "Father" → Sun. Multiple matches render all of them (Open Question 4).
6. **Related Warga Kendara selection**: the "related" warga chart per sub-tag is a **mapping to be confirmed by the domain** (e.g. Marriage → D9, Career → D10 in a later phase). Phase 1 can only reference the available warga entries (`d1`, `d9`, `suryaLagna`, `chandraLagna`); until confirmed, a sensible default per sub-tag is proposed (Open Question 5).
7. **Color classification (proposed default)**: a planet tag is **green** when its `PlanetaryStrength` is positive (Athi Uchcha 1.25, Uchcha 1, Moolatrikona 0.75, Own Sign 0.5, Mitra 0.1), **red** when negative (Neecha −1, Athi Neecha −1.25, Shatru −0.1), **white** otherwise (Sama 0). House-load / Nakshatra-load / warga tags follow the confirmed domain rule (Open Questions 2–3). This default is a placeholder until the domain defines "good/bad" per observation kind.
8. **Storage convention**: student data (geometry, selection state, observation tags, result notes) persists on `HoroscopeNote`; system observations are render-time derivations from `CalculatedDetails` (+ `wargaKendara`), never stored — the `currentPlanets`/`wargaKendara`-fallback precedent.
9. **Catalogs**: the house-purpose catalog and planet-signification catalog are static system-wide display data resolved via i18n; English/Sanskrit is authoritative from the feature doc; Sinhala translations are pending.
10. **Numeric-enum conventions** apply throughout: planets 1-9, signs 1-12, houses 1-12, `PlanetaryStrength` values, `TagColor` for student tags — never display strings in storage. Parent tags are `0` = "Other" or `1`-`12` = house number.
11. **Result notes** are notepad-level (matching "based on all observations"), plain text, newest-first. Per-parent-tag grouping is an Open Question.

## Open Questions

1. **Definition of "house load" (භාව භාරය), "house load position", "Nakshatra load of the house load" and "position of the Nakshatra load"** — these terms appear ONLY in `docs/student-notes.md`; they are not defined anywhere in the repository. Proposed working interpretation: "house load" = the planets occupying the house (or a computed load value for the house); "house load position" = the position (sign/degree) of that load; "Nakshatra load of the house load" = the Nakshatra lord of the house-load position; "position of the Nakshatra load" = the position of that Nakshatra lord. The domain must provide the authoritative definitions and any calculation rules before the derivation can be implemented. (Domain)
2. **Green/red/white classification rule per observation kind** — what exactly makes a house load, Nakshatra load, or warga observation "good" (green) vs "bad" (red)? The doc says "If some strength is good… If something is bad…" — the domain must define the goodness/badness rule for each of the six observation sub-sections (planet strength sign is proposed as the default for planet tags; load/warga rules are unspecified). (Domain)
3. **"Related Warga Kendara" selection** — which warga chart(s) count as "related" for a selected sub-tag? Phase 1 has only `d1`, `d9`, `suryaLagna`, `chandraLagna` available. Proposed default: a per-subject warga mapping (Marriage → D9, Career → D10 when available, etc.). Confirm the mapping or provide guidance. (Domain)
4. **Sub-tag → relevant planet(s) mapping** — confirm that the mapping is the reverse lookup on the planet-signification table (all matching planets show), and confirm whether "etc…" in the feature doc implies additional sub-tags beyond the house-table significations (the table's comma-separated lists are the assumed sub-tag source). (Domain)
5. **"The D1 load in the Warga Kendara"** — proposed interpretation: the planet(s) that load the selected house in the D1 chart, shown by their position and details in the related warga chart. Confirm this reading. (Domain)
6. **Sinhala strings** — the feature doc provides English (and Sanskrit) only. Authoritative Sinhala translations are needed for: the 12 parent-tag labels, the Sanskrit names as displayed in Sinhala, all sub-tag labels, the planet-signification lines, section headers, ratio labels, and the notepad UI strings. (Domain/PM)
7. **TagColor palette** — the doc says the student "should possible to select the color" without naming a palette. Proposed provisional palette: green/red/white/blue/yellow/purple (numeric `TagColor` 1-6). Confirm the exact palette and its Sinhala/English names. (UX/Domain)
8. **Notepad availability scope** — confirm the notepad is available on the horoscope detail page for own, public and share-linked horoscopes (assumed), and whether it should also appear on search result cards or anywhere else. (PM/UX)
9. **Super Admin visibility** — can a Super Admin read a student's notepad content (support/debugging), or is the notepad strictly private to the student like SearchBookmark? Default assumed: strictly private. (Domain/PM)
10. **Selection-state persistence** — should the last-selected parent/sub-tag and the open/closed state restore when the notepad reopens (stored in `notepadState`), or reset on every open? (UX)
11. **Manual-horoscope limits** — which observation sections can derive for manual horoscopes (Chandra/Surya Lagna rotation works; Nakshatra-load sections may need Nakshatra data that manual charts may lack)? Confirm the expected behaviour per section on manual charts. (Domain/Architect)
12. **Observation-text length caps** — maximum length for student observation tags and result notes (proposed default 500 chars / 2000 chars — confirm). (PM/UX)

## Out of Scope

- **New astrological calculations** — the notepad derives everything from existing `CalculatedDetails` (+ `wargaKendara`); no new ephemeris/varga calculations. (New derived "load" values on `CalculatedDetails` are only added if the confirmed load definitions require them — Open Questions 1–2.)
- **Sharing or exporting notepad content** — notes are private; no share links, no PDF/CSV export of notes, no search integration
- **Collab/multi-student notepads** — no shared or teacher-reviewed notes
- **Changes to the horoscope detail page outside the notepad popup** — charts, tables, tabs, settings stay as-is
- **No new user settings, roles or permission changes** — the notepad reuses the existing Student role; no new roles (e.g. no "teacher" role)
- **Mobile-optimized notepad redesign** — the notepad is a desktop-first popup in phase 1; touch behaviour is handled but no separate mobile layout is designed (see Open Questions)
- **Other varga charts (D2–D60) in the warga observation sections** — phase 1 references only `d1`, `d9`, `suryaLagna`, `chandraLagna` (consistent with the Warga Kendara phasing)
