## 1. Overview

The calculations tab of the horoscope detail page gains a **ෂඩ් බලය (Shad Bala)** table: 8 columns (ග්රහයා / Planet, ස්ථාන බල, චේෂ්ටා බලය, කාල බලය, දිග් බලය, දෘෂ්ඨි බලය, නෛසර්ගික බලය, අනුපාතය) × 9 rows (Sun..Ketu). Each bala renders as a **checkbox** (checked = the planet has the bala); every checkbox carries a **reason tooltip** for both its checked and unchecked state; toggles **auto-save** (500 ms debounce, last-write-wins) and persist as **overrides** that survive the AstrologySettings full recalculation. Non-owners and share-link viewers see the table **read-only**.

**UX goals:**

1. **Compare at a glance** — the table's job is cross-planet comparison of the six strengths; the desktop grid keeps all 54 checkboxes + ratios visible without scrolling (the ratio column makes a weak/strong planet obvious).
2. **Explain every state** — the tooltip is the core study aid: checked boxes list *why* they are checked, unchecked boxes list *why not* (and when the system simply cannot compute a bala, that is said explicitly).
3. **Correction-first editing** — any bala can be toggled (the student is never restricted to "non-calculable" cells); the flip is instant, the save is invisible unless it fails, and the override dot quietly marks what the student has locked.
4. **Zero-flicker legacy** — legacy horoscopes without stored `shadbalaya` render the computed values on first paint (synchronous lazy recompute at render), never an all-unchecked flash.
5. **Bilingual parity** — every label, reason, toast and aria string ships in Sinhala and English under `astrology.shadbalaya.*`, reusing `astrology.planetNames.*` for planet names.

## 2. Answers to the routed UX open questions

### 2.1 BA OQ7 — does a toggle that equals the computed value still show as overridden?

**Decision: YES — the override dot and the sticky semantics apply whenever `overridden === true`, regardless of whether the toggled value coincides with the computed value.**

Architect already resolved the storage semantics (toggle always writes `overridden: true`; it is sticky — Clarifying Assumption 4, US-SB-008 edge case). The UI must reflect this honestly:

- The dot appears the moment the student toggles (optimistically) and stays after the save succeeds — even if the box's final state matches what the system would have computed.
- The tooltip adds the footer line "Set manually — kept through recalculation" whenever `overridden === true`.
- Rationale: the semantic the student needs to see is *"this value is user-locked and will survive a settings recalculation"* — that is true whether or not it matches the computed value. Hiding the dot on a coincidental match would imply the value is recomputable and invite confusion after a future recalculation changes other planets.

### 2.2 BA OQ8 / Architect OQ5 — manual-override visual indicator

**Decision: a small indigo dot (•) pinned to the top-right corner of the checkbox cell**, plus a legend line under the section title. The dot is **not** color-only — it is also conveyed via the checkbox `aria-label` suffix and the tooltip override footer line.

| Option considered | Verdict |
|-------------------|---------|
| **Dot badge top-right of the cell (chosen)** | Minimal footprint across 54 cells; works identically for checked and unchecked boxes; never competes with the check mark itself; can carry a `title` on hover |
| Cell border/background tint | Rejected — color-only indicator fails the contrast/not-color-alone guidance and tints 54 cells visually noisy |
| Strikethrough on the checkbox | Rejected — visually conflicts with the checked state and reads as "cancelled" |
| Star/asterisk glyph | Rejected — noisier than a dot and ambiguous against the existing `ⓘ` tooltip glyph |
| Tooltip-only (architect v1 fallback) | Rejected — the override is a persistent data property, not a hover-time detail; hiding it behind a tooltip hides the "this survives recalculation" property from scanning |

**Spec of the dot:** 6px circle, `bg-indigo-600`, absolute at the cell's top-right (`top-1 right-1`), `aria-hidden="true"` (decorative — the state is announced via the checkbox `aria-label`), `title={t("astrology.shadbalaya.override.title")}` for mouse hover. Cell gets `relative` positioning. Legend line under the section header: `astrology.shadbalaya.override.hint`.

## 3. User Flows

### 3.1 Flow: view the table

```
Horoscope Detail → Calculations tab → scroll past the Planets table →
  → ෂඩ් බලය section renders (sync compute → first paint populated, no flicker) →
  → Desktop: 8-column table, 9 planet rows, checkbox per bala, (n/6) ratio per row →
  → Mobile (<640px): card-per-planet, 3×2 grid of labeled bala checkboxes + ratio →
  → Hover/focus/tap any checkbox → reason tooltip (checked or unchecked reasons) →
  → Override dots mark student-set balas; legend line explains them →
```

### 3.2 Flow: toggle a bala (auto-save)

```
Student (owner or super-admin) → click a bala checkbox →
  → Optimistic: box flips immediately; that row's ratio (n/6) updates instantly →
  → Override dot appears in the cell (optimistic) →
  → Debounce timer (500 ms) starts for (planet, bala); a second toggle on the same
    key cancels and restarts it → last write wins →
  → Timer fires → PATCH /api/horoscope/:id/shadbalaya { planet, bala, value } →
    → 200 { planet, bala, value, overridden: true } → silent (dot stays; no toast) →
    → 401/403/404/400/500 → revert box + ratio + dot → error toast →
  → Student navigates away with a pending timer → keep-alive flush fires the last toggle
```

### 3.3 Flow: read-only view (non-owner / share link)

```
Student opens a public horoscope owned by another student, or a share link →
  → isEditable = false → Shad Bala section renders the same table/cards →
  → Checkboxes render disabled (checked/unchecked state preserved, not interactive) →
  → Each cell shows a focusable ⓘ button (visible on hover/focus, always keyboard-reachable)
    that opens the same reason tooltip →
  → Ratio column, override dots and tooltips render exactly as in the editable view →
  → Any hand-crafted mutation → API rejects (403) regardless of UI
```

### 5.2 Mobile (< 640px) — `block sm:hidden` card-per-planet

Follows the planets-table mobile pattern (page.tsx line ~1656) — cards in a `space-y-2` stack. Rationale for **cards over horizontal scroll**:

- The adjacent planets table uses cards at this breakpoint; two adjacent sections switching presentation differently would be jarring.
- 8 columns on a 360px phone would force either sub-40px checkbox hit areas or horizontal scroll; cards give every checkbox a labeled 44px+ chip target.
- The six bala names (e.g. `චේෂ්ටා බලය`, `නෛසර්ගික බලය`) become readable labels instead of cryptic narrow column headers.

```
│ └────────────────┘ └────────────────┘        │
│ (3×2 grid of labeled bala checkbox chips)    │
└──────────────────────────────────────────────┘
```

| Element | Spec |
|---------|------|
| Card | `border rounded overflow-hidden` (same as the planets mobile card); header row `px-3 py-2 flex items-center gap-2` |
| Header | Glyph + localized name (`☉ රවි`), `font-medium text-sm`; ratio right-aligned `ml-auto` (`text-sm text-gray-700`) |

## 6. Checkbox Cells

### 6.1 Visual design — real native checkboxes

**Decision: native `<input type="checkbox">`, not a custom toggle.**

Rationale: the repo has **no custom checkbox component** — `PlanetaryOrbsSection` uses native number inputs, `RashiAspectsSection` uses a single `role="switch"` for a one-off toggle. A 54-cell grid is exactly what native checkboxes are for: free Space-key activation, free checked-state announcement, native focus handling, and no custom ARIA to get wrong. The settings `role="switch"` pattern is for single binary switches with labels, not dense grids.

| Property | Spec |
|----------|------|
| Element | `<input type="checkbox">` |
| Size | `h-4 w-4` (16px) |
| Color | `accent-indigo-600` (Tailwind accent utility — repo has no existing accent usage, indigo-600 is the primary token; if the project's Tailwind version lacks `accent-*`, use `accent-[#4F46E5]` or the `--primary` token via a small CSS class) |
| Focus | visible ring — `focus-visible:ring-2 focus-visible:ring-indigo-500 rounded-sm` (repo focus-ring convention) |
| Label association | Each checkbox is wrapped in a `<label>` (editable) so the hit area extends past the 16px box (desktop: `p-1` around the box; mobile chip: the whole chip) — touch target ≥ 44px on mobile |
| Keyboard | Native — Tab to focus, Space to toggle (no custom handler needed) |
| States | `checked`, `unchecked`, `disabled` (read-only), plus the override dot (§6.2) |

### 6.2 Override indicator

- **Rendering condition:** `bala.overridden === true`.
- **Visual:** 6px dot, `bg-indigo-600`, `rounded-full`, absolutely positioned `top-1 right-1` in the (relatively positioned) cell / mobile chip. `aria-hidden="true"` + `title={t("astrology.shadbalaya.override.title")}`.
- **Why not color-only:** the checkbox `aria-label` gains the suffix `, set manually` (`astrology.shadbalaya.override.ariaShort`), and the tooltip renders the override footer line (§7.2), so the state is available to screen readers and hoverers alike.
- **Optimistic timing:** the dot appears immediately on toggle (the save *will* set `overridden: true`) and is removed together with the value revert on save failure.
- **Sticky display:** the dot persists across reloads and shows even when the toggled value equals the computed value (§2.1).
- **Legend:** `astrology.shadbalaya.override.hint` renders under the section title when at least one dot is present (US-SB-013 is otherwise invisible to the student — the legend is the only place that explains the recalculation guarantee).
- **Read-only views:** dots still render (the stored `overridden` flags are part of the read-only data).

### 6.3 Read-only mode (US-SB-014)

**Decision: render `disabled` checkboxes + a focusable `ⓘ` tooltip trigger per cell — do not remove the checkboxes.**

- Rationale: removing the boxes would reflow the grid and break cross-column scanning; `disabled` preserves the exact visual state and communicates "this value exists but is not yours to change" (matching `PlanetaryOrbsSection`'s `readOnly` treatment — same layout, non-interactive values).
- `disabled` checkbox: native `disabled` attribute (removed from tab order, announced by SR as disabled with its checked state).
- Tooltip access: each cell/chip adds a small `ⓘ` button — `text-gray-400 hover:text-indigo-700`, `aria-label={t("astrology.shadbalaya.infoGlyph")}` (reuses the `aspectReason.infoGlyph` naming pattern) — styled `opacity-0 group-hover:opacity-100 focus:opacity-100` (appears on row hover, always reachable by keyboard). It opens the same reason tooltip (§7) and is the only focusable element in the cell.
- The ratio column, dots and tooltips render unchanged (US-SB-014 AC2).
- The section header may carry a small read-only notice (`astrology.shadbalaya.readOnlyNotice`) for share-link contexts, following the `ManagedByAdminNotice` informational style.

## 7. Tooltips (the core study aid)

### 7.1 Mechanism — custom tooltip reusing the AspectChip/AspectTooltip pattern

**Decision: a custom out-of-flow tooltip identical in mechanics to `AspectChip`/`AspectTooltip`** (native `title` alone is insufficient — it cannot render multi-line structured content and has no focus styling), with the `title` attribute kept as a **plain-text fallback** for no-JS/print (exactly as `AspectChip` does).

| Mechanic | Spec (mirrors `AspectChip.tsx`) |
|----------|--------------------------------|
| Trigger | Editable: the checkbox's wrapping `<label>` (hover/focus/tap). Read-only: the `ⓘ` button |
| Open | `mouseenter` → 150 ms hover timer (flicker guard); `focus` opens immediately; tap toggles |
| Close | `mouseleave`, `blur`, `Escape` (returns focus to the trigger), tap-outside |
| Positioning | Out-of-flow `position: fixed` computed from the trigger rect; flips above/below; clamped to viewport (`Math.min(Math.max(left, 160), window.innerWidth - 160)` per AspectChip); re-positions on scroll/resize |
| Width | `max-w-[280px]` EN / `max-w-[320px]` SI (Sinhala is ~15–20% wider — existing convention) |
| Singleton | Only one tooltip open at a time (opening one closes the previous) |
| ARIA | `aria-describedby={open ? tooltipId : undefined}` on the trigger → `role="tooltip"` element with `id`; `title` fallback carries the **full plain text** |
| z-index | Above the table and sticky headers (`z-50`) |

**Component:** new `ShadBalaCheckbox` (owns the tooltip state) + `ShadBalaTooltip` (presentational, styled like `AspectTooltip`: `rounded-lg border bg-white shadow-lg z-50 px-3 py-2`). The shared open/position logic can be lifted into a tiny hook (`useBalaTooltip`) mirroring AspectChip's timers.

### 7.2 Content structure

Tooltip body, top to bottom:

1. **Heading** — the bala name, bold 13px: `astrology.shadbalaya.balaNames.*` (e.g. `ස්ථාන බල` / `Sthana Bala`).
2. **State + reason line(s)**:
   - Checked: `✓ {t("astrology.shadbalaya.tooltip.checkedBecause")}` then **one line per reason**, each resolved via `t(reason.key, reason.params)` with numeric enum params substituted per locale (sign/house/strength names via existing `astrology.signNames.*` / `astrology.planetNames.*` where the template uses them).
   - Unchecked: `✗ {t("astrology.shadbalaya.tooltip.uncheckedBecause")}` then one line per reason (e.g. Sthana `Neecha + Shatru`, Naisargika `Maranakaraka (in house 4)`).
   - Empty reasons (`[]`): a single line `astrology.shadbalaya.reason.manual` ("Set manually — the system cannot calculate this bala"). Drishti always carries the explicit `drishti.reason.manual` variant.
3. **Override footer** — when `overridden === true`: hairline-separated line `astrology.shadbalaya.tooltip.override` ("Set manually — kept through recalculation"), styled like the aspect tooltip's `Δ` footer (`border-t`, 12px, `text-gray-500`).

Reason lines: 12px `text-gray-700`, `leading-[1.5]`, one per line (US-SB-009 AC3 — a Cheshta planet that is both Vakra and Shukla-Chandra-conjunct lists both lines). The `✓`/`✗` glyphs are language-neutral; numerals stay Western in both locales (app convention).


The override footer renders on every tooltip whose bala is `overridden: true`, checked or unchecked (§2.1).

### 7.4 Tooltip accessibility

| Requirement | Design |
|-------------|--------|
| Keyboard | Trigger is a real focusable element (checkbox label / `ⓘ` button); `focus` opens, `blur` closes, `Escape` closes and restores focus |
| Screen reader | `aria-describedby` → `role="tooltip"`; the checkbox's own `aria-label` carries state + override suffix; `title` fallback = the full plain text (heading, state line, all reasons, override line) |
| Timing | 150 ms hover-open delay only; no auto-dismiss while hovered/focused (WCAG 1.4.13) |
| Contrast | Tooltip surface `bg-white` + `border`; reason text `text-gray-700` (≥ 4.5:1); footer `text-gray-500` (≥ 4.5:1 at 12px — verify, else bump to `text-gray-600`) |
| Motion | 120 ms fade + 2px translate; disabled under `prefers-reduced-motion` |

## 8. Interaction & Auto-Save

### 8.1 Toggle flow (US-SB-008)

```
Click/Space on checkbox →
  1. Optimistic flip: local state value toggles; ratio (n/6) recomputes from the six
     local flags instantly (US-SB-010 AC3)
  2. Override dot appears (optimistic)
  3. Debounce map: pending[`${planet}:${bala}`] = { value } ; clear any existing timer
     for that key and start a new 500 ms timer (last-write-wins)
  4. Timer fires → PATCH /api/horoscope/:id/shadbalaya { planet, bala, value }
  5. Success → silent (no toast — see §8.3); dot stays
  6. Failure → revert value + ratio + dot to the pre-toggle state → error toast
```

- **Rapid toggling:** consecutive toggles on the same (planet, bala) settle on the latest value — the timer restarts each time, so at most one PATCH per key is in flight after quiescence (US-SB-008 edge case). Toggles on *different* keys may produce overlapping PATCHes — each key is independent (server `$set` is per dotted path, no cross-key races).
- **Persistence:** the saved state is server-stored — survives refresh, navigation and logout (US-SB-008 AC3). On reload the page re-merges `mergeShadBalaya(computed, stored)` and the stored (overridden) value wins.
- **Re-sync:** the component re-syncs its local state from props when they change (e.g. after an AstrologySettings recalculation refresh — arch note).
- **Debounce value:** 500 ms per architect decision (BA OQ9 resolved). This is long enough to absorb quick multi-toggles, short enough that a single toggle feels immediate.

### 8.2 Navigation race

The 500 ms window means a toggle made just before navigating away can be dropped when the component unmounts (the timer is cleared). UX requirement: **flush pending saves on navigation** — a keep-alive `fetch(..., { keepalive: true })` (or `navigator.sendBeacon`) fired from a `beforeunload` listener and a `useEffect` cleanup that fires any pending key immediately when the component unmounts. Failure during flush is silent (no toast possible mid-navigation); the next page load shows the server value. This is a UX recommendation on top of the architect's "no sendBeacon needed" note — the architect's rationale (toggles don't affect navigation state) is about *correctness of the route change*, not about *silent loss of the last toggle*; the student's study correction deserves the best-effort flush. **Flag for Developer/QA** (see §16).

### 8.3 Feedback — decision on toast/indicator

| Feedback | Decision | Rationale |
|----------|----------|-----------|
| Success toast | **None** | 54 toggles × toast = noise; the checkbox flip + ratio + dot *are* the feedback. The privacy toggle toasts because it is a rare, semantically weighty action — a bala toggle is a frequent, low-stakes study correction |
| Auto-saving indicator | **None** | 500 ms debounce is imperceptible; a spinner would strobe during rapid toggling. The override dot appearing (persisted state confirmed) is the quiet success signal |
| Error | **Toast** | `astrology.shadbalaya.toast.saveError`, type `error`, 5 s auto-dismiss, `fixed top-4 right-4 z-50 bg-red-600 text-white` (existing toast pattern, page.tsx line ~849); checkbox/ratio/dot revert simultaneously |
| Pending save indicator | **None** | Same rationale as auto-saving indicator |

### 8.4 Loading/saving state treatment

- **No full-table spinner** on load — the resolved data is computed synchronously at render (§9).
- While a PATCH for a key is in flight, the checkbox stays enabled (rapid toggling must never be blocked); last-write-wins is enforced by the timer reset, and the server accepts any value.
- `aria-busy` is not needed on the table (no async render); if Developer adds a transient in-flight marker, it must be non-visual (e.g. `aria-disabled` on the single checkbox while its PATCH is in flight is acceptable — **not** recommended, since it blocks rapid toggling).

## 9. Empty / Legacy / Not-Computed States

### 9.1 Legacy horoscope without stored `shadbalaya` (no flicker)

- The page resolves `shadbalaya = mergeShadBalaya(computeShadBalaya(planets, houses, ctx), calculatedDetails.shadbalaya)` **synchronously during render** (pure module, no ephemeris, no I/O — arch Decision #7). Therefore **first paint is the populated state**: all computable boxes already checked, reasons already composed. There is no "all unchecked then populate" sequence and **no shimmer/loading placeholder is needed**.
- If a future implementation must compute asynchronously (e.g. data not yet fetched), the table must render nothing (not an all-unchecked table) until the resolved value exists — the requirement is *never show a wrong state*. Recommended approach remains the synchronous `useMemo` path so this case never arises.
- The first toggle on a legacy document creates the sparse stored record (only that bala) via the PATCH route; the page merge fills the remainder at render (arch §Legacy documents).

### 9.2 Balas the system cannot compute

These render **unchecked** with an explanatory tooltip (US-SB-012, US-SB-007):

| Case | Tooltip reason |
|------|----------------|
| Drishti bala — every horoscope, both sources | `astrology.shadbalaya.drishti.reason.manual` ("Set manually — the system cannot calculate Drishti bala") |
| Cheshta Uttarayana on manual horoscopes (no birth time) | Covered by the sign-based fallback when Ravi is in signs 10–12/1–2; when not, the bala is unchecked with `reason.manual` |
| Cheshta planet-war condition (deferred in v1 — no war module; auto) | Unchecked with `reason.manual` until the condition lands (the `warWinner` key exists for when it does) |
| Kala varga-load condition (deferred; auto) | Unchecked with `reason.manual` until the load formula is confirmed |
| Kala day/night on manual horoscopes without birth time | `ctx.day` absent → day/night conditions skipped; unchecked with `reason.manual` |
| Rahu/Ketu Dig bala | Always unchecked with `reasons: []` → the tooltip shows the generic `reason.manual` line |

The student may toggle **any** of these (US-SB-008 AC1 — no restriction to "non-calculable" balas); a toggle marks `overridden: true` and persists (US-SB-012 AC5).

### 9.3 Error/load states

- Table data comes from the already-loaded horoscope payload — **no independent fetch**, so no dedicated load-error state. If the resolved `shadbalaya` is absent/undefined (defensive), render the table with all boxes unchecked + `reason.manual` tooltips (US-SB-001 edge case) and log a console warning — never a blank section.
